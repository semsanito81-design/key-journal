# 🔑 Журнал учёта ключевых носителей

Веб-приложение для ведения журнала выдачи ключевых носителей (токенов/смарт-карт) и учёта сертификатов сотрудников. Пришло на замену Excel-таблице и автоматизирует расчёт сроков действия сертификатов, ведение базы сотрудников и печать актов приёма-передачи с электронной подписью.

## 🚀 Основные возможности

- **Журнал носителей:** учёт JaCarta, eToken, смарт-карт.
- **Сертификаты:** на одном физическом носителе может быть несколько сертификатов (2FA, ЦОД, Оператор, Админ) с разными сроками действия.
- **Автоматический расчёт:** система сама считает дату окончания сертификата исходя из его типа (2 года / 1 год), исключая ошибки человеческого фактора.
- **Подсветка статусов:** интерфейс предупреждает, если до окончания сертификата осталось менее 60 дней, и подсвечивает просроченные.
- **Электронная подпись:** сотрудник расписывается прямо на экране планшета/мышкой при получении ключа, подпись сохраняется в БД и автоматически выводится в печатном Акте.
- **Печать актов:** формирование акта приёма-передачи в формате А4 (Landscape) с корректной версткой (сохранение в PDF).
- **База сотрудников:** ведение справочника сотрудников с импортом/экспортом в CSV.
- **Умный фильтр:** при выдаче нового носителя в выпадающем списке предлагаются только те сотрудники, у которых ещё нет ключа.
- **Роли и аудит:** разделение прав (Админ, Оператор, Аудитор), логирование всех действий в аудит-лог.

## 🛠 Технологический стек

- **Frontend:** Vanilla JS, HTML5, CSS3 (без тяжелых фреймворков), библиотека `SignaturePad` (для подписи), `SheetJS` (для работы с Excel).
- **Backend:** Node.js, Fastify, PostgreSQL (нативный драйвер `pg`).
- **Аутентификация:** JWT (через httpOnly cookies), пароли хешируются (PBKDF2).

## 🗄 Архитектура базы данных

Проект использует реляционную базу данных PostgreSQL. Структура спроектирована так, чтобы избежать дублирования данных и обеспечить строгий учёт (каждый носитель может содержать несколько сертификатов с разными сроками).

### Таблицы

#### 1. `users` (Пользователи системы)
Хранит учётные записи для доступа к веб-интерфейсу.
- `id` (UUID, PK) — уникальный идентификатор.
- `login` (TEXT, UNIQUE) — логин для входа.
- `full_name` (TEXT) — ФИО пользователя.
- `role` (TEXT) — роль (`admin`, `operator`, `auditor`).
- `salt` (TEXT) — соль для хеширования пароля.
- `hash` (TEXT) — хеш пароля (PBKDF2).
- `active` (BOOLEAN) — флаг активности (можно заблокировать вход).
- `created` (TIMESTAMPTZ) — дата создания.
- `last_login` (TIMESTAMPTZ) — дата последнего входа.

#### 2. `employees` (Справочник сотрудников)
База людей, которые получают ключи. Позволяет автоматически подставлять должности при выдаче.
- `id` (UUID, PK) — уникальный идентификатор.
- `full_name` (TEXT) — ФИО сотрудника.
- `position` (TEXT) — должность.
- `department` (TEXT) — подразделение.
- `is_active` (BOOLEAN) — флаг (уволенные скрываются из списков).
- `created_at` (TIMESTAMPTZ) — дата добавления.

#### 3. `cert_types` (Справочник типов сертификатов)
Определяет бизнес-правила: какие бывают сертификаты и сколько они живут.
- `code` (SMALLINT, PK) — код типа (1, 2, 3, 4).
- `name` (TEXT) — короткое имя (2FA, ЦОД, Оператор, Админ).
- `title` (TEXT) — полное название.
- `default_valid_years` (SMALLINT) — **срок действия в годах** (например, 2 для 2FA и 1 для Оператора). От этого поля зависит автоматический расчёт даты окончания.
- `description` (TEXT) — примечание.

#### 4. `carriers` (Ключевые носители)
Физические токены и смарт-карты (то, что выдается на руки).
- `id` (UUID, PK) — уникальный идентификатор.
- `ppp` (INT) — порядковый номер в журнале.
- `issue_date` (DATE) — дата выдачи ключа.
- `carrier_type` (TEXT) — модель (JaCarta PKI, eToken 5110 и т.д.).
- `carrier_serial` (TEXT) — серийный номер самого носителя.
- `employee` (TEXT) — ФИО получателя.
- `position` (TEXT), `department` (TEXT) — должность и подразделение на момент выдачи.
- `status` (TEXT) — статус носителя (`active`, `returned`, `reserved`).
- `signature_data` (TEXT) — **электронная подпись** (картинка в формате Base64).
- `return_mark` (DATE), `sign_cert`, `sign_carrier`, `two_factor` — служебные поля (отметка о возврате, росписи, флаг 2FA).
- `created` (TIMESTAMPTZ), `updated` (TIMESTAMPTZ) — служебные метки времени.

#### 5. `certificates` (Сертификаты)
Сертификаты, записанные на конкретный носитель. Один носитель может содержать несколько сертификатов (связь **один-ко-многим**).
- `id` (UUID, PK) — уникальный идентификатор.
- `carrier_id` (UUID, FK) — **ссылка на носитель** (`carriers.id`).
- `cert_type` (SMALLINT, FK) — **ссылка на тип** (`cert_types.code`).
- `serial_number` (TEXT) — серийный номер самого сертификата.
- `valid_from` (DATE) — дата выпуска сертификата.
- `valid_to` (DATE) — дата окончания (рассчитывается автоматически через VIEW).
- `status` (TEXT) — статус (`active`, `revoked`, `reserved`).
- `note` (TEXT) — примечания.

#### 6. `audit` (Аудит-лог)
Логирует все действия пользователей для безопасности.
- `id` (UUID, PK) — уникальный идентификатор.
- `ts` (TIMESTAMPTZ) — время события.
- `user_id` (UUID, FK) — кто сделал действие (`users.id`).
- `user_name` (TEXT) — ФИО на момент события.
- `action` (TEXT) — тип действия (`login`, `carrier_create`, `cert_update` и т.д.).
- `entity` (TEXT), `entity_id` (UUID) — к какому объекту относится действие.
- `details` (JSONB) — детали (старые/новые значения).

### Представления (VIEW)

#### `v_certificates` (Умное представление сертификатов)
Это ключевой элемент архитектуры. Вместо того чтобы хранить дату окончания в таблице (что привело бы к ошибкам при изменении справочника), мы вычисляем её «на лету».
- Объединяет таблицу `certificates` с `cert_types`.
- Берёт `valid_from` и прибавляет `default_valid_years` из справочника типов.
- Отдаёт фронтенду готовое поле `valid_to` без сдвигов часовых поясов.

### Схема связей (ER Diagram)
```text
  users (1) ─────< (0..N) audit
  cert_types (1) ─────< (0..N) certificates
  carriers (1) ─────< (0..N) certificates
  employees (независимая таблица-справочник для автозаполнения)

⚙️ Установка и запуск (через OSPanel)

Проект оптимизирован для работы в связке с OSPanel на Windows. Ниже описана пошаговая инструкция по развертыванию с нуля.
1. Требования

    OSPanel (с установленным модулем PostgreSQL-17).

    Node.js версии 18 или выше.

    Git (для клонирования репозитория).

2. Подготовка базы данных

    Запустите OSPanel и включите модуль PostgreSQL-17 (он должен гореть зеленым).

    Откройте консоль PostgreSQL (через трей OSPanel или DBeaver).

    Создайте базу данных и пользователя, выполнив следующие SQL-команды:
    sql

    CREATE DATABASE key_journal;
    CREATE USER kcj_app WITH PASSWORD 'ваш_надежный_пароль';
    GRANT ALL PRIVILEGES ON DATABASE key_journal TO kcj_app;
    \c key_journal
    GRANT ALL ON SCHEMA public TO kcj_app;

    (Обратите внимание: в OSPanel по умолчанию порт PostgreSQL — 5433, а не 5432).

3. Клонирование и настройка проекта

    Откройте терминал (PowerShell или cmd), перейдите в папку доменов OSPanel и склонируйте проект:
    bash

    cd D:\OSPanel\home
    git clone https://github.com/ваш-логин/key-journal.git
    cd key-journal

    Создайте файл конфигурации .env из шаблона:
    bash

    Copy-Item .env.example .env

    Откройте .env в любом редакторе и укажите ваши данные (особенно пароль от БД и порт):
    env

    PORT=3000
    DATABASE_URL=postgresql://kcj_app:ваш_надежный_пароль@127.0.0.1:5433/key_journal
    JWT_SECRET=придумайте_длинную_случайную_строку
    JWT_EXPIRES=8h

4. Установка зависимостей и миграция

Выполните в терминале (в папке проекта):
bash

# Установка всех npm-пакетов
npm install

# Создание таблиц, представлений (VIEW) и администратора по умолчанию
npm run migrate

После выполнения команды migrate в базе появятся все таблицы и учетная запись admin (пароль: admin123).
5. Запуск сервера
bash

npm run dev

Если в консоли появилось сообщение 🚀 http://key-journal → http://127.0.0.1:3000, значит сервер успешно запущен.
6. Настройка домена в OSPanel (Опционально)

Чтобы обращаться к журналу по красивому адресу, а не по IP:

    В трее OSPanel выберите «Домены» → «Добавить».

    Имя домена: key-journal.local.

    Папка: D:\OSPanel\home\key-journal\public.

    Включите проксирование на Node.js (порт 3000).

    В файле C:\Windows\System32\drivers\etc\hosts (открыть от имени администратора) добавьте строку:
    127.0.0.1 key-journal.local

Теперь приложение доступно по адресу http://key-journal (или http://127.0.0.1:3000, если домен не настраивали).
⚠️ Возможные проблемы при запуске

    Ошибка ECONNREFUSED 127.0.0.1:5432 — в .env указан неверный порт. В OSPanel PostgreSQL обычно работает на порту 5433.

    Ошибка кодировки (кракозябры) при миграции — убедитесь, что SQL-файлы миграции сохранены в кодировке UTF-8 без BOM.

    Ошибка прав доступа к VIEW — если база восстанавливалась из бэкапа, выполните: GRANT SELECT ON v_certificates TO kcj_app;.

👤 Учётные записи по умолчанию

После выполнения миграции создаётся администратор:

    Логин: admin

    Пароль: admin123

Обязательно смените пароль в разделе «Профиль» после первого входа!
📦 Резервное копирование

Так как GitHub хранит только код, базу данных нужно бэкапить отдельно.
Для создания дампа базы выполните (из корня проекта):
bash

pg_dump -U kcj_app -h 127.0.0.1 -p 5433 key_journal > backup.sql

Для восстановления:
bash

psql -U kcj_app -h 127.0.0.1 -p 5433 -d key_journal -f backup.sql
